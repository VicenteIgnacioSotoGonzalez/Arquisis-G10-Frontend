# Cliente SSE autenticado · E3-032, E3-034, E3-052 y E3-053

`src/services/sse.js` incorpora un cliente separado de `apiFetch()` para consumir `GET /events/stream` con un access token de Auth0. La opción **Actividad en vivo** de la pantalla principal abre el panel E3-052.

## Origen por ambiente

El panel abre `GET /events/stream` en el origen de `VITE_SSE_ORIGIN`. El valor contiene esquema, host y puerto si corresponde. La ruta la añade el cliente. Los ambientes remotos requieren HTTPS y el HTTP local se limita a loopback. La falta de configuración detiene el panel antes de solicitar un token. `VITE_API_URL` conserva la base de los demás endpoints.

| Ambiente | Configuración de compilación de Vite |
| --- | --- |
| Local | Copiar `.env.example` a `.env.local` y ajustar `VITE_SSE_ORIGIN=http://localhost:8001` al puerto de Master de prueba o al origen HTTPS del proxy local. |
| Staging | Compilar con `npm run build -- --mode staging` y establecer `VITE_SSE_ORIGIN` con el origen HTTPS confirmado en staging. |
| Producción | Fijar `VITE_SSE_ORIGIN` al origen HTTPS dedicado confirmado para ese ambiente antes de `npm run build`. |

Las variables `VITE_*` forman parte del bundle público. Usar variables del entorno de compilación para el dominio, el client ID y el audience de Auth0. Mantener claves y tokens fuera de la configuración. En ambos Master, autorizar el origen exacto de la SPA en `CORS_ALLOWED_ORIGINS`. En Auth0, verificar Allowed Web Origins, Callback URLs y Logout URLs para ese mismo origen, y comprobar que los operadores reciben `read:events` para el audience configurado. El origen dedicado de E3-053 evita pasar el SSE por la HTTP API v2.

El panel enlaza el servicio SSE con la cuenta activa de Auth0 mientras está montado. Salir del panel, cerrar sesión o cambiar de cuenta aborta la conexión anterior y descarta la lista visible. Volver a abrirlo recupera el cursor guardado para esa cuenta y autorización. El panel conserva en memoria los últimos 100 eventos de la vista, por ID de publicación descendente, y muestra la hora de captura en la zona local del navegador.

El cliente abre un `fetch` CORS con Bearer en `Authorization`, omite cookies, rechaza redirecciones, interpreta UTF-8 de forma incremental y descarta tramas incompletas, inválidas y duplicadas. Avanza el cursor cuando termina `onEvent`, incluso si el callback devuelve una promesa. Usa `Last-Event-ID` y backoff para reconectar después de un corte. Los comentarios del stream mantienen la conexión y no avanzan el cursor.

El panel pide el scope `read:events` mediante un cliente Auth0 con caché en memoria, ligado al montaje de la vista. La renovación silenciosa depende de la sesión de Auth0 y puede requerir volver a iniciar sesión si el navegador impide el acceso a esa sesión. En `localStorage`, el servicio SSE guarda únicamente el ID público precedido por una clave derivada de la API, emisor, sujeto, audiencia y permisos. La misma cuenta con la misma autorización puede recuperar su cursor al entrar de nuevo. Los tokens y los eventos quedan fuera del almacenamiento SSE. Si el navegador bloquea almacenamiento o criptografía, la conexión conserva el cursor en memoria.

Ante un `401`, el panel limpia la lista y solicita un token fresco una vez. Si la renovación falla por sesión inválida o el servidor vuelve a responder `401`, el panel pide iniciar sesión de nuevo. Un `403` detiene la conexión, limpia la lista y descarta su cursor. Al expirar el JWT en una conexión activa, el cliente deja de leer y reanuda con un token fresco y el último ID procesado. Un `400` o `409` elimina el cursor y emite `invalid-cursor`. La vista debe limpiar su historial visible antes de abrir deliberadamente una conexión desde el comienzo. Un `503` o un error de transporte conserva el cursor y espera entre 1 y 15 segundos entre reintentos, con retardo exponencial. El navegador realiza el preflight automáticamente. Los fallos de preflight, red y TLS pueden verse como el mismo error de conexión en JavaScript.

## Plan E2E en navegador

1. Abrir la SPA de staging y comprobar que un visitante anónimo ve la invitación a iniciar sesión sin una petición al feed.
2. Entrar como operador de prueba con `read:events`. En Network, confirmar que el navegador usa el host SSE HTTPS dedicado, que `OPTIONS` acepta el origen de la SPA y los headers `Authorization` y `Last-Event-ID` cuando se solicitan, y que el `GET` devuelve `200` y `text/event-stream`. Inspeccionar sólo nombres de headers y estados, sin exportar ni copiar credenciales.
3. Generar dos eventos de prueba en momentos distintos. Confirmar que el primero aparece en pantalla antes de generar el segundo, en una misma conexión. Confirmar un heartbeat en un intervalo sin actividad.
4. Interrumpir la red, restaurarla y comprobar que la nueva petición lleva `Last-Event-ID` y que el panel evita duplicados. Con un token de prueba de corta duración, confirmar la renovación y el mismo cursor. Salir del panel o cerrar sesión y comprobar que se cancela el `GET`.
5. Entrar con una cuenta sin permiso, o revocar el acceso de la cuenta operadora. Comprobar que `403` detiene el feed y deja la lista vacía. Verificar en un origen de prueba excluido de CORS que el navegador impide leer el feed.

La verificación desde el dominio desplegado requiere configurar el host SSE, Auth0 y CORS de staging.
